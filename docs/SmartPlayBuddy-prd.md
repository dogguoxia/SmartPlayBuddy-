## 2. 背景与问题

当前 SmartPlayBuddy 客户端已具备：
- WebSocket 实时连接、JWT 认证、统一消息封装（`command` / `response` / `system` / `session` / `error`）
- 键盘 / 鼠标 / 屏幕捕获驱动
- 截图回传能力

但现有模式是"人工在手机端点按 → 客户端执行单条指令"，存在以下痛点：

1. **体力浪费**：崩坏星穹铁道、原神等游戏存在每日体力 / 委托上限，玩家上班 / 学习时无法清体力，体力溢出造成长期资源损失。
2. **脚本门槛高**：能写自动脚本的玩家极少，现有脚本普遍因游戏更新、UI 变化而失效，维护成本高。
3. **无反馈闭环**：纯指令执行无法感知游戏画面状态，遇到弹窗、加载、体力不足等异常情况会"卡死"。
4. **安全信任问题**：用户不信任第三方脚本（封号风险、木马风险）。

## 3. 产品目标

**一句话目标**：用户用自然语言向智能体提出"帮我清原神体力"这样的需求，智能体自主完成"截图观察 → 编写 DSL 脚本 → 安全审查 → 下发客户端执行 → 截图反馈"的闭环，实现日常代肝。

具体目标：

| 目标 | 描述 | 衡量指标 |
|------|------|----------|
| 代肝可用 | 崩坏星穹铁道、原神每日委托 / 清体力自动化 | 单个任务完整执行成功率 ≥ 90% |
| 零门槛 | 用户仅需自然语言描述需求 | 用户无需编写或理解脚本 |
| 安全可信 | 所有脚本经独立子智能体安全审查后才下发 | 危险指令拦截率 100% |
| 可观测 | 全流程截图留证、进度可见 | 关键节点均有截图记录 |

## 4. 范围

### 4.1 本期范围（In Scope）

- 客户端截图能力增强（定时、按需、回传）
- DSL 脚本规范定义 + 客户端解释执行器
- TOS 对象存储接入（截图 / 脚本存档）
- 客户端 ↔ 服务器需求 / 任务通信接口
- 服务器 Docker 部署 FastGPT，构建超级智能体 + 2 个子智能体
- 游戏适配（按优先级顺序）：崩坏星穹铁道 → 原神

### 4.2 非目标（Out of Scope）

- 游戏账号操作（不碰账号密码，用户自行登录）
- 破解 / 反外挂对抗（不做任何绕过检测的手段）
- 付费代肝交易系统（本版本不做计费）
- 移动端游戏自动化（仅 PC 客户端）

## 5. 术语表

| 术语 | 说明 |
|------|------|
| 代肝 | 代替玩家完成游戏内的日常重复操作（清体力、委托等） |
| DSL | 面向游戏自动化的领域专用语言（本系统定义为 JSON 指令流，见 §9） |
| 超级智能体 | 部署在 FastGPT 上的编排大脑，负责任务拆解与调度 |
| 子智能体 1 | 脚本编写智能体：根据截图与用户需求生成 DSL |
| 子智能体 2 | 安全审查智能体：对 DSL 做安全合规检查 |
| TOS | 对象存储服务（火山引擎 TOS 或同类 S3 兼容对象存储），用于存放游戏截图与脚本 |
| 体力 | 游戏内每日恢复的行动力资源（星穹铁道开拓力 / 原神树脂） |

## 6. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│                        用户（PC 端）                         │
│  游戏客户端（星穹铁道 / 原神）      SmartPlayBuddy 客户端      │
│         ▲                                  │ 截图 │ 需求 │    │
│         │ 操作（键盘/鼠标）                 ▼       ▼       │
│  ┌──────┴───────┐        ┌─────────────┐ ┌──────────────┐  │
│  │  DSL 执行器   │◄───────│ 客户端主循环  │ │  截图服务     │  │
│  │ (解释+安全隔离) │        └──────┬──────┘ └──────┬───────┘  │
│  └──────────────┘                 │ WebSocket(JSON)│         │
└───────────────────────────────────┼────────────────┼─────────┘
                                    ▼                ▼
┌─────────────────────────── 服务器（云主机）────────────────────┐
│  ┌──────────────┐  需求/任务  ┌────────────────────────────┐  │
│  │  FastGPT     │◄───────────│  网关服务（Docker）          │  │
│  │  (Docker)    │            │  - 任务队列 / 状态管理       │  │
│  │  超级智能体   │── 截图查询 ─→│  - TOS 客户端              │  │
│  └──────┬───────┘            │  - WebSocket 服务端         │  │
│         │ 拆解                └────────────┬───────────────┘  │
│  ┌──────▼───────┐                          │                  │
│  │ 子智能体1     │  DSL 脚本  ┌────────────▼────┐             │
│  │ 脚本编写     │───────────→│ 子智能体2         │             │
│  └──────────────┘            │ 安全审查          │             │
│        ▲                     └────────┬─────────┘             │
│        │ 截图（图像理解）              │ 通过后下发              │
│        └─────────────────────────────┘                        │
│  ┌─────────────────────────────────────────────────────────┐  │
│  │  TOS 对象存储：game-screenshots / dsl-scripts / tasks    │  │
│  └─────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

**数据流（以"清原神体力"为例）**：

1. 用户点击客户端"AI 代肝"→ 输入需求"帮我用树脂清一下体力"
2. 客户端截图（当前游戏画面 + 背包/树脂状态页）→ 上传 TOS → 连同需求文本通过 WebSocket 发给服务器网关
3. 网关创建任务，通知 FastGPT 超级智能体
4. 超级智能体：读取 TOS 截图 → 判断当前游戏状态 → 委派子智能体 1 编写 DSL
5. 子智能体 1：结合截图 + 需求生成 DSL 脚本（含"截图比对"与"循环/等待"逻辑）
6. 超级智能体将 DSL 交给子智能体 2 做安全审查（禁用键、危险指令、资源锁定检查）
7. 审查通过 → 网关将 DSL 推送给对应客户端
8. 客户端 DSL 执行器逐条执行，关键步骤截图回传 → 上传 TOS → 服务器更新任务进度
9. 任务结束：服务器汇总截图与结果，用户可在客户端查看"代肝报告"

## 8. 功能需求

### FR-1 客户端截图（优先级 P0，先行实现）

| 编号 | 需求 | 验收标准 |
|------|------|----------|
| FR-1.1 | 按需截图并回传 base64 / 上传 TOS | 现有 `screen_operate("screenshot")` 基础上，支持指定 `save` 路径后自动上传 TOS |
| FR-1.2 | 定时 / 循环截图（用于任务过程留证） | 任务执行中按配置间隔截图，失败不中断执行 |
| FR-1.3 | 截图压缩与格式控制 | JPEG 质量可配，单张 ≤ 1MB，上传带宽可控 |
| FR-1.4 | 本地截图管理 | 复用调试面板 `list_screenshots` / `delete_screenshot`，增加"上传状态"标记 |

### FR-2 客户端需求提交（P0）

| 编号 | 需求 | 验收标准 |
|------|------|----------|
| FR-2.1 | 客户端 UI 提供需求输入框（自然语言） | 用户输入中文需求即可发起任务 |
| FR-2.2 | 提交时携带上下文截图 | 提交包内含当前画面截图（TOS 链接 + 缩略图 base64） |
| FR-2.3 | 任务状态可视化 | 客户端展示任务：排队 → AI 分析 → 审查中 → 执行中 → 完成/失败 |

### FR-3 DSL 脚本规范与解释执行（P0）

见 §9 完整定义。验收标准：
- 客户端新增 `dsl` 执行入口，可解释执行 JSON DSL
- 支持节点类型：键盘 / 鼠标 / 截图 / 图像匹配 / OCR 比对 / 等待 / 循环 / 跳转 / 上报
- 单步异常可配置策略：`retry`（重试 N 次）/ `skip` / `abort` / `notify`（通知服务器）
- 执行器受全局"急停"开关控制，用户随时可终止

### FR-4 图像识别基础能力（P0.5）

| 编号 | 需求 | 说明 |
|------|------|------|
| FR-4.1 | 模板匹配 | 在截图帧中查找目标图（用于"找到'委托'按钮点击"） |
| FR-4.2 | OCR 文字识别 | 识别体力数值 / 弹窗文字（PaddleOCR 或云 OCR） |
| FR-4.3 | 模板图管理 | 模板图存 TOS，客户端按需拉取；游戏更新后由超级智能体重新截取 |

### FR-5 TOS 对象存储（P0.5）

| 编号 | 需求 | 说明 |
|------|------|------|
| FR-5.1 | Bucket 规划 | `game-screenshots/{userId}/{taskId}/`、`dsl-scripts/{userId}/`、`templates/` |
| FR-5.2 | 上传接口 | 客户端直传（预签名 URL）或经服务器中转，二选一，优先预签名直传 |
| FR-5.3 | 权限与生命周期 | 私有桶 + 时效签名；截图保留 30 天，任务报告保留 90 天 |

### FR-6 服务器网关服务（P1）

| 编号 | 需求 | 说明 |
|------|------|------|

| FR-6.2 | 在线设备管理 | 维护设备 ↔ 用户 ↔ WebSocket 连接映射（扩展现有 claim 协议） |
| FR-6.3 | 任务状态机 | `created → analyzing → scripting → reviewing → approved → executing → done / failed / cancelled` |
| FR-6.4 | DSL 下发行权 | 仅下发"审查通过 + 指定设备在线"的脚本 |

### FR-7 FastGPT 部署（P1）

| 编号 | 需求 | 说明 |
|------|------|------|
| FR-7.1 | Docker Compose 部署 | 单机 docker-compose 一键起 FastGPT + 依赖（MongoDB / PG / OneAPI 或直接接 LLM API） |
| FR-7.2 | 知识库 | 内置：DSL 规范文档、游戏 UI 模板图说明、风险操作清单 |
| FR-7.3 | 工作流编排 | 用 FastGPT 工作流实现超级智能体编排（§10） |

### FR-8 超级智能体与子智能体（P1）

| 编号 | 需求 | 说明 |
|------|------|------|
| FR-8.1 | 超级智能体（编排） | 接收需求 + 截图；决策：当前画面状态 → 目标 → 任务拆解；调度子智能体 1/2 |
| FR-8.2 | 子智能体 1（脚本编写） | 输入：需求文本 + 若干截图（TOS 链接 + 图像理解结果）；输出：完整 DSL 脚本 + 运行说明 |
| FR-8.3 | 子智能体 2（安全审查） | 输入：DSL 脚本 + 运行环境说明；输出：`pass` / `reject` + 修改建议；**reject 则回退子智能体 1 重写**（最多 N 轮） |
| FR-8.4 | 审核记录审计 | 每次 pass / reject 的完整对话与理由入库，可回溯 |

### FR-9 游戏适配（P2，有先后顺序）

| 优先级 | 游戏 | 首批任务 | 说明 |
|--------|------|----------|------|
| 第一 | 崩坏星穹铁道 | 每日委托、清开拓力（体力）、领取任务奖励 | 回合制 + 自动战斗 + 寻路简单，UI 状态稳定，**优先适配** |
| 第二 | 原神 | 每日委托、树脂清体力（合成浓缩树脂）、尘歌壶 | 开放世界，画面复杂，依赖图像识别更高，后置 |

选择顺序理由：星穹铁道画面元素相对固定、无复杂地形寻路、支持自动战斗，DSL 成功率更高，利于先验证闭环；原神地图大、场景光照变化大，图像匹配难度高。

## 9. DSL 脚本规范（草案）

### 9.1 设计原则

- **JSON 描述、人类可读**：AI 生成友好、用户可审阅
- **状态可控**：每个步骤可带条件、超时、失败策略
- **安全隔离**：解释器强制白名单动作集，拒绝一切未知动作

### 9.2 顶层结构

```json
{
  "version": 1,
  "game": "honkai_star_rail",
  "name": "每日委托-清体力",
  "settings": {
    "screen_interval": 5000,
    "max_duration": 1800000,
    "screenshot_evidence": true
  },
  "steps": []
}
```

### 9.3 步骤节点类型（`steps[]` 元素）

| 节点 | 示例 | 说明 |
|------|------|------|
| `keyboard` | `{"action":"keyboard","operate":"tap","key":"f"}` | 复用现有键盘驱动 |
| `mouse` | `{"action":"mouse","operate":"move_to","x":800,"y":450,"duration":0.3}` | 复用现有鼠标驱动 |
| `wait` | `{"action":"wait","seconds":2}` | 等待（游戏加载） |
| `screenshot` | `{"action":"screenshot","save":"step_01.jpg","evidence":true}` | 截图留证并上传 |
| `match` | `{"action":"match","template":"委托.png","threshold":0.85,"then":{"mouse":{...}},"else":{"jump":5}}` | 图像匹配条件分支 |
| `ocr` | `{"action":"ocr","expect":{"contains":"体力不足"},"then":{"jump":"end"}}` | OCR 文字条件分支 |
| `loop` | `{"action":"loop","times":3,"steps":[...]}` | 循环子步骤块 |
| `report` | `{"action":"report","message":"正在执行第 2 轮"}` | 向服务器上报进度 |

```json
{
  "action": "match",
  "template": "委托按钮.png",
  "threshold": 0.85,
  "timeout": 10000,
  "then": [
    {"action": "mouse", "operate": "tap", "button": "left"}
  ],
  "else": [
    {"action": "report", "message": "未找到委托按钮，截图上报"}
  ],
  "fail_policy": "notify"
}
```

### 9.4 失败策略（`fail_policy`）

| 取值 | 行为 |
|------|------|
| `retry` | 自动重试（配套 `retry_times` / `retry_interval`） |
| `skip` | 跳过本步继续 |
| `abort` | 终止任务，上报失败 |
| `notify` | 截图 + 上报服务器，等服务器指令（人工 / 智能体介入） |

## 10. 服务器智能体编排（FastGPT 工作流）

```
用户需求 + 上下文截图(TOS)
        │
        ▼
超级智能体：意图理解 & 状态判断
   │ 需要更多信息？──► 下发"补充截图"指令（要求用户截图指定页面）
   │
   ▼
子智能体 1：编写 DSL
   │ 产出：dsl.json + 说明
   ▼
子智能体 2：安全审查
   │ 检查项：
   │  1. 动作白名单（仅 keyboard/mouse/screenshot/wait/loop/match/ocr/report）
   │  2. 禁止指令：系统键组合（Alt+F4 / Ctrl+Alt+Del / Win 键）、按住超时、无限循环
   │  3. 参数边界：坐标必须落在屏幕范围内、循环次数 ≤ 50、单步超时 ≤ 60s
   │  4. 资源风险：脚本总时长 ≤ 用户设定上限
   │  5. 隐私风险：截图仅回传至用户自己的 TOS 空间
   │  通过？──是──► 入库 + 下发客户端执行
   │   └──否──► 附修改意见，回子智能体 1 重写（≤ 3 轮，仍不通过则转人工拒绝）
```

## 11. 通信协议扩展（基于现有消息格式）

沿用现有统一结构（`type / action / data(Base64-JSON) / requestId / timestamp`），新增 action：

| 方向 | type | action | data 说明 |
|------|------|--------|-----------|
| 客户端→服务器 | `command` | `submitTask` | 需求文本 + 截图 TOS 链接 + 设备信息 |
| 服务器→客户端 | `command` | `runDsl` | 完整 DSL JSON |
| 客户端→服务器 | `response` | `runDsl` | 执行结果：完成 / 失败 + 截图列表 |
| 客户端→服务器 | `response` | `executeStep` | 逐步回执（进度上报） |
| 服务器→客户端 | `command` | `stopTask` | 紧急停止当前任务 |
| 客户端→服务器 | `command` | `uploadComplete` | 截图上传 TOS 完成通知（附 objectKey） |

## 12. 非功能需求

| 类别 | 要求 |
|------|------|
| 性能 | 图像匹配单帧 ≤ 500ms；DSL 步骤间调度开销 ≤ 100ms；截图上传不阻塞执行线程 |
| 安全 | 全部传输走 JWT；DSL 执行器白名单硬编码、不读环境变量；TOS 私有桶 + 签名 URL |
| 可靠性 | 断线重连（已有）后续传任务状态；执行中客户端崩溃 → 服务器标记任务失败并通知 |
| 合规 | 客户端启动任务前二次确认"承担游戏账号风险"；提供全局急停快捷键（如 F12） |
| 可观测 | 全链路日志（客户端 / 网关 / FastGPT）；任务报告含每步截图时间线 |

## 13. 实施顺序与里程碑

| 里程碑 | 内容 | 依赖 | 交付物 |

|------|------|------|
| 游戏版本更新导致 UI 变化、脚本失效 | 高 | 模板图存 TOS 集中管理；失败截图自动回流 AI 重新识别并更新模板 |
| AI 生成危险 / 失控指令 | 高 | 子智能体 2 硬规则审查 + 执行器白名单 + 用户急停（双重保险） |
| 自动操作被游戏判定违规 | 中 | 温和操作（不模拟人类点击随机偏移范围）、限速、用户自担风险确认 |
| 图像识别误判（场景相似） | 中 | OCR + 模板双重校验；关键动作前强制截图留证 |
| 网络 / TOS 上传慢 | 低 | 预签名直传 + 压缩 + 失败重试队列 |

## 15. 验收标准（关键场景）

1. 用户在星穹铁道内（任意界面）发起"清开拓力"，系统自动完成：识别体力图标 → 打开地图 → 传送 → 选择关卡 → 自动战斗 → 结算领取，全程无需人工，成功率 ≥ 90%。
2. 子智能体 1 生成的任意 DSL 均被子智能体 2 审查；危险样例（如 `Alt+F4`、100 万次循环、屏幕外坐标）100% 被拦截。
3. 任务执行期间任一节点用户按急停，10ms 内停止所有输入动作。
4. 同一账号重复任务期间，服务器拒绝并发任务下发。
5. 原神任务在星穹铁道验证通过后进入适配，验收标准同场景 1。
