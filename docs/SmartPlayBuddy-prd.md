## 2. 背景与问题

当前 SmartPlayBuddy 客户端已具备：
- WebSocket 实时连接、JWT 认证、统一消息封装（`command` / `response` / `system` / `session` / `error`）
- 键盘 / 鼠标 / 屏幕捕获驱动
- 截图回传能力

但现有模式是"人工在手机端点按 → 客户端执行单条指令"，存在以下痛点：

1. **体力浪费**：崩坏星穹铁道、原神等游戏存在每日体力 / 委托上限，玩家上班 / 学习时无法清体力，体力溢出造成长期资源损失。
2. **脚本门槛高**：能写自动脚本的玩家极少，现有脚本普遍因游戏更新、UI 变化而失效，维护成本高。
3. **无反馈闭环**：纯指令执行无法感知游戏画面状态，遇到弹窗、加载、体力不足等异常情况会"卡死"。
4. **安全信任问题**：用户不信任第三方脚本（封号风险、木马风险）。

## 3. 产品目标

**一句话目标**：用户用自然语言向智能体提出"帮我清原神体力"这样的需求，智能体自主完成"截图观察 → 基于客户端成熟模块编排 DSL → 安全审查 → 下发客户端执行 → 截图反馈"的闭环，实现日常代肝。

**核心思路（分层）**：**成熟的游戏脚本模块放在客户端**（`mods/` 目录，开发者 / 社区维护、经安全审查的**整任务动作单元**：刷本、领取奖励等一整套动作，含进本 → 自动战斗 → 结算领取的全流程）；**DSL 脚本只做"体力编排"**（编排层：根据当前体力计算刷局次数、体力检查与分支、预留体力、奖励领取顺序），AI 永不直接写底层键盘 / 鼠标操作。由此把"AI 生成不可信底层操作"的安全面收窄为"AI 只算体力、只调度白名单整任务模块"，详见 §9。

具体目标：

| 目标 | 描述 | 衡量指标 |
|------|------|----------|
| 代肝可用 | 崩坏星穹铁道、原神每日委托 / 清体力自动化 | 单个任务完整执行成功率 ≥ 90% |
| 零门槛 | 用户仅需自然语言描述需求 | 用户无需编写或理解脚本 |
| 安全可信 | 所有编排 DSL 经独立子智能体安全审查后才下发，且底层动作仅能来自白名单模块 | 危险编排拦截率 100% |
| 可观测 | 全流程截图留证、进度可见 | 关键节点均有截图记录 |

## 5. 术语表

| 术语 | 说明 |
|------|------|
| 代肝 | 代替玩家完成游戏内的日常重复操作（清体力、委托等） |
| 游戏脚本模块（Module） | 客户端内置的成熟、已验证、经安全审查的**整任务动作单元**（如"刷本""领取奖励"），内部实现一整套动作（进本 → 自动战斗 → 结算领取等），对外只暴露"模块名 + 参数 + 结构化结果（含体力/状态）"的接口 |
| 编排 DSL | 面向游戏自动化的**体力编排语言**（JSON 指令流）：根据当前体力计算刷局次数、预留体力、体力不足分支与循环，仅调度白名单整任务模块，**不含任何底层操作原语**，见 §9 |
| 模块库（Mods 库） | 客户端 `mods/` 目录中的整任务游戏脚本模块集合，随客户端版本发布或由服务器签名下发 |
| 超级智能体 | 部署在 FastGPT 上的编排大脑，负责任务拆解与调度 |
| 子智能体 1 | 体力编排智能体：读取体力数值（截图 OCR / 模块返回），**计算体力编排流程并生成编排 DSL** |
| 子智能体 2 | 安全审查智能体：对编排 DSL 与模块调用做安全合规检查 |
| TOS | 对象存储服务（火山引擎 TOS 或同类 S3 兼容对象存储），用于存放游戏截图与脚本 |
| 体力 | 游戏内每日恢复的行动力资源（星穹铁道开拓力 / 原神树脂） |

## 6. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│                        用户（PC 端）                         │
│  游戏客户端（星穹铁道 / 原神）      SmartPlayBuddy 客户端      │
│         ▲                                  │ 截图 │ 需求 │    │
│         │ 操作（键盘/鼠标）                 ▼       ▼       │

│  │  编排 DSL 执行器 │◄───────│ 客户端主循环  │ │  截图服务     │  │
│  │ (调 mods/ 模块)  │        └──────┬──────┘ └──────┬───────┘  │
│  │ (解释+安全隔离) │        └──────┬──────┘ └──────┬───────┘  │
│  └──────────────┘                 │ WebSocket(JSON)│         │
└───────────────────────────────────┼────────────────┼─────────┘

┌─────────────────────────── 服务器（云主机）────────────────────┐
│  ┌──────────────┐  需求/任务  ┌────────────────────────────┐  │
│  │  FastGPT     │◄───────────│  网关服务（Docker）          │  │
│  │  (Docker)    │            │  - 任务队列 / 状态管理       │  │
│  │  超级智能体   │── 截图查询 ─→│  - TOS 客户端              │  │
│  └──────┬───────┘            │  - WebSocket 服务端         │  │
│         │ 拆解                └────────────┬───────────────┘  │
│  ┌──────▼───────┐                          │                  │
│  │ 子智能体1     │ 编排 DSL   ┌────────────▼────┐             │
│  │ 体力编排     │───────────→│ 子智能体2         │             │
│  └──────────────┘            │ 安全审查          │             │
│        ▲                     └────────┬─────────┘             │
│        │ 截图（图像理解）              │ 通过后下发              │

│  └─────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

**数据流（以"清原神体力"为例）**：

1. 用户点击客户端"AI 代肝"→ 输入需求"帮我用树脂清一下体力"
2. 客户端截图（当前游戏画面 + 背包/树脂状态页）→ 上传 TOS → 连同需求文本通过 WebSocket 发给服务器网关
3. 网关创建任务，通知 FastGPT 超级智能体
4. 超级智能体：读取 TOS 截图 → 判断当前游戏状态 → 委派子智能体 1 做体力编排
5. 子智能体 1：结合截图（体力数值）+ 需求 + 客户端模块清单，计算体力编排（当前体力 → 每局消耗 → 预留 → 可刷局数），生成编排 DSL（loop 刷本 + 领奖 + 体力分支）
6. 超级智能体将编排 DSL 交给子智能体 2 做安全审查（模块白名单、参数 schema、循环 / 时长边界、体力账校验）
7. 审查通过 → 网关将编排 DSL 推送给对应客户端
8. 客户端编排 DSL 执行器逐条调用本地 `mods/` 模块执行，关键步骤截图回传 → 上传 TOS → 服务器更新任务进度
9. 任务结束：服务器汇总截图与结果，用户可在客户端查看"代肝报告"

**FR-1 技术实现路径（已落地）**：

| 层 | 技术选型 | 说明 |
|----|----------|------|
| 抓帧 | **dxcam**（DXGI Desktop Duplication） | 仅 Windows；返回 BGRX 4 通道 `numpy.ndarray`（alpha 恒 0） |
| 降级 | **GDI**（PIL `ImageGrab`） | DXGI 不可用（远程接管 / 驱动异常 / 锁屏等）时自动降级，结果经 `backend: "dxcam" \| "gdi"` 标记 |
| 色彩空间 | **OpenCV** `COLOR_BGRA2RGB` | 统一 `_to_rgb()`：4 通道 BGRX → 3 通道 RGB，避免 PIL 误判 RGBA 导致 alpha=0 全透明（PNG 打不开） |
| 编码 | **Pillow**（PNG / WebP）+ **OpenCV** `imencode`（JPEG） | 编码前统一 3 通道 RGB；`fmt` / `format` 键名均兼容 |
| 进程隔离 | **子进程 + 二进制帧协议**（`drivers/host.py` + `registry.py`） | 驱动独立进程运行，主进程经 stdin/stdout 通信；帧格式 `<BII`（type + json_len + bin_len）+ JSON 元数据 + 二进制 body，大帧（截图数据）走独立 body，避免 bytes 无法 JSON 序列化 |
| 依赖隔离 | pip `--target packages/` | 按驱动 `requirements.txt` 独立安装，不污染主环境 |
| 应用层 | 调试面板 `ui/debugger.py` | `screenshot(monitor, save)` → 调用 screen 驱动 capture → base64 预览 + 落盘；`choose_save_dir()` 调系统 `FOLDER_DIALOG` 选择保存目录 |
| 前端 | `debugger.html`"截图预览"页 | 实时预览图 + 尺寸 + 完整保存路径显示 |

**实测数据**：默认 `scale 0.5`（2560×1600 → 1280×800），单帧 PNG ≈ 230KB，单次截图延迟 ≈ 200–500ms（受编码尺寸影响）。

### FR-3 模块库与体力编排 DSL 执行（P0）

成熟整任务脚本模块（刷本、领取奖励）存放在客户端，DSL 只做体力编排（见 §9 完整定义）。验收标准：
- 客户端内置模块库 `mods/`，首批含至少 2 个整任务示例模块（如"刷本""领取奖励"）
- 客户端新增 `dsl` 执行入口，可解释执行编排 DSL（仅 `module` / `check` / `wait` / `loop` / `report` 节点）
- 模块对外接口统一：`{mod, params} → {status, state, data}`；模块返回体力 / 局数等结构化数据供编排计算；模块名 + 参数均经白名单与 schema 校验，未知模块 / 越界参数直接拒绝
- 体力编排能力：按"当前体力、每局消耗、预留体力"计算刷局次数，体力不足自动停止 / 通知
- 单步异常可配置策略：`retry`（重试 N 次）/ `skip` / `abort` / `notify`（通知服务器）
- 执行器受全局"急停"开关控制，用户随时可终止

## 9. 模块与体力编排 DSL 规范（草案）

### 9.1 分层思想

```
┌──────────────────────────────────────────────────────────┐
│  编排层（AI 生成，仅此层可被 AI 编写）                      │
│  DSL 脚本 = 体力编排：算体力 → 排流程 → 调度模块            │
│  例：读取体力=120，每局消耗40，预留20 → 可刷 2 局 →          │
│       loop 2 次 { mods.hsr.run_stage(刷本) }               │
│       → mods.common.claim_rewards(领取奖励) → report       │
├──────────────────────────────────────────────────────────┤
│  模块层（客户端 mods/，开发者 / 社区维护，成熟已验证）        │
│  每个模块 = 一整套动作（整任务单元）                         │
│  • mods.hsr.run_stage：刷本（进本 → 自动战斗 → 结算领取）    │
│  • mods.common.claim_rewards：领取奖励（遍历领取入口）       │
│  对外只暴露 {mod, params} → {status, state, data}          │
├──────────────────────────────────────────────────────────┤
│  原语层（现有驱动）                                        │
│  keyboard / mouse / screen（dxcam+GDI 降级）驱动，          │
│  仅被模块内部使用，AI 与 DSL 均不可直接触达                 │
└──────────────────────────────────────────────────────────┘
```

**安全收益**：AI 与用户 DSL 永远接触不到底层原语，只能调度白名单整任务模块；即使 AI 编排再激进，最终动作仍是模块内部预先审查过的一整套动作。游戏更新只需维护模块实现，存量编排 DSL 无需重写。

### 9.2 设计原则

- **JSON 描述、人类可读**：AI 生成友好、用户可审阅
- **模块黑盒（整任务）**：模块 = "刷本""领奖"级别的完整动作，DSL 不关心其内部步骤
- **体力驱动编排**：DSL 只算体力账（当前体力、每局消耗、预留、可刷局数）并据此排流程
- **状态可控**：模块返回结构化结果（含剩余体力 / 局数 / 奖励状态）供分支判断
- **安全隔离**：模块名 + 参数 schema 双重白名单校验，拒绝一切未知调用

### 9.3 模块清单（客户端 `mods/`，首批示例）

模块粒度 = **整任务一整套动作**：

| 模块 | 适用游戏 | 说明 | 内部能力（一整套动作） |
|------|----------|------|----------------------|
| `mods.hsr.run_stage` | 星铁 | 刷本 | 选关 → 进本 → 自动战斗 → 结算 → 领取战利品，一局一个完整流程 |
| `mods.common.claim_rewards` | 通用 | 领取奖励 | 遍历各奖励入口（任务 / 邮件 / 委托）→ 逐个点击领取 → 确认领取完成 |
| `mods.hsr.daily_quest` | 星铁 | 每日委托 | 接取委托 → 逐项刷完 → 委托面板领取奖励 |
| `mods.gi.run_domain` | 原神 | 刷秘境 | 选秘境 → 进本 → 自动战斗 → 结算 → 领取 |
| `mods.gi.resin_refine` | 原神 | 合成浓缩树脂 | 打开合成台 → 批量合成 → 领取 |

模块元数据（随客户端 `mods/` 目录发布）：

```json
{
  "name": "mods.hsr.run_stage",
  "version": "1.2.0",
  "game": "honkai_star_rail",
  "description": "刷本：选关→进本→自动战斗→结算→领取战利品",
  "params_schema": {
    "stage": {"type": "string", "enum": ["stagnant_shadow", "calyx_golden", "calyx_crimson"]},
    "energy_per_run": {"type": "integer", "min": 1, "max": 240}
  },
  "states": ["stage_cleared", "energy_insufficient", "battle_failed", "stage_locked"],
  "returns": {"energy_after": "integer", "runs_done": "integer"},
  "sha256": "…"
}
```

**模块返回体力数据**（`returns.energy_after`）：每次刷本模块结算时回报剩余体力，编排层据此实时修正后续局数——体力编排的闭环数据来源。

### 9.4 体力编排模型

DSL 的核心是**算体力账**，由子智能体 1 完成：

```
当前体力 E0（截图 OCR / 用户上报 / 模块返回）
每局消耗 C（模块参数 energy_per_run）
预留体力 R（用户偏好：如保证还能再打一局或自动回复不溢出）
可刷局数 N = floor((E0 - R) / C)          → loop 次数
第 i 局后剩余体力 Ei = Ei-1 - C            → check 体力是否仍 ≥ R
体力不足 / 恢复未满 → wait（按恢复速率预估）或 notify（等用户决定）
```

| 概念 | 说明 |
|------|------|
| 当前体力 | 初始值来源：截图 OCR 识别 / 客户端读取 / 模块返回 |
| 每局消耗 | 模块参数 `energy_per_run`，模块元数据提供建议值 |
| 预留体力 | 用户偏好（默认保留一局消耗量），避免体力被刷空后影响手动游玩 |
| 可刷局数 | `floor((E0 - R) / C)`，超上限防呆（≤ 50 局） |
| 恢复预估 | 体力不足时按恢复速率计算等待时长（可选 `wait`）或转 `notify` |

### 9.5 顶层结构

```json
{
  "version": 3,
  "game": "honkai_star_rail",
  "name": "刷本-清体力",
  "settings": {
    "max_duration": 3600000,
    "screenshot_evidence": true,
    "required_mods": ["mods.hsr.run_stage@^1", "mods.common.claim_rewards@^1"],
    "energy": {"current": 120, "cost_per_run": 40, "reserve": 20}
  },
  "steps": []
}
```

`required_mods` 声明依赖模块及其版本范围，执行前客户端校验存在性与参数 schema；`energy` 记录编排时的体力账，供审查与执行校验。

### 9.6 编排节点类型（`steps[]` 元素）

| 节点 | 示例 | 说明 |
|------|------|------|
| `module` | `{"action":"module","mod":"mods.hsr.run_stage","params":{"stage":"calyx_golden"}}` | 调用整任务模块（一整套动作） |
| `check` | `{"action":"check","ref":"step_1","expect":{"energy_after":{">=":20}},"then":{"jump":"step_2"},"else":{"jump":"end"}}` | 按模块返回的体力 / 状态条件分支 |
| `wait` | `{"action":"wait","seconds":1800}` | 等待体力恢复 / 游戏加载 |
| `loop` | `{"action":"loop","times":2,"steps":[{"action":"module","mod":"mods.hsr.run_stage","params":{...}}]}` | 循环刷局（次数 = 体力编排计算值） |
| `report` | `{"action":"report","message":"第 1/2 局完成，剩余体力 80"}` | 向服务器上报进度 |

体力编排 DSL 示例（星铁刷本 + 领奖）：

```json
{
  "action": "module",
  "mod": "mods.hsr.run_stage",
  "params": {"stage": "calyx_golden"},
  "timeout": 600000,
  "fail_policy": "notify",
  "then": {"action": "loop", "times": 2, "steps": [
    {"action": "module", "mod": "mods.hsr.run_stage", "params": {"stage": "calyx_golden"}}
  ]},
  "after": {"action": "module", "mod": "mods.common.claim_rewards"}
}
```

模块调用结果统一为 `{status: "ok"|"error"|"timeout", state: <模块状态>, data: {energy_after, runs_done, ...}}`，`check` 节点按 `data` 或 `state` 跳转；`status != "ok"` 时按 `fail_policy` 处理。

### 9.7 失败策略（`fail_policy`）

| 取值 | 行为 |
|------|------|
| `retry` | 自动重试（配套 `retry_times` / `retry_interval`） |
| `skip` | 跳过本步继续 |
| `abort` | 终止任务，上报失败 |
| `notify` | 截图 + 上报服务器，等服务器指令（人工 / 智能体介入） |

### 9.8 模块库管理

| 项 | 方案 |
|----|------|
| 发布渠道 | 随客户端版本内置为主；热更新模块由服务器签名下发（版本 + sha256，校验后落盘 `mods/`） |
| 安全审查 | 模块进入客户端前必须通过安全审查（同 §10 子智能体 2 标准），实现代码可审计 |
| 生命周期 | 游戏更新导致模块失效 → 客户端上报失败截图 → 维护者更新模块版本，存量 DSL 不变 |
| 版本兼容 | 编排 DSL 声明 `required_mods` 版本范围；客户端模块升级不破坏旧 DSL |

## 10. 服务器智能体编排（FastGPT 工作流）

```
用户需求 + 上下文截图(TOS，含体力数值 OCR) + 客户端模块清单
        │
        ▼
超级智能体：意图理解 & 状态判断
   │ 需要更多信息？──► 下发"补充截图"指令（如体力面板截图）
   │ 目标模块缺失？──► 提示用户更新客户端模块库（不尝试绕过）
   ▼
子智能体 1：体力编排计算
   │ 输入：需求 + 截图（体力数值）+ 模块清单（模块名/参数 schema/状态集/每局消耗）
   │ 计算：当前体力 → 每局消耗 → 预留 → 可刷局数 N → 体力不足分支
   │ 产出：编排 DSL（loop N 次刷本 + 领取奖励 + 体力 check/wait/report）+ 说明
   ▼
子智能体 2：安全审查
   │ 检查项：
   │  1. 模块白名单（仅允许 required_mods 已声明的整任务模块，禁止未注册模块名）
   │  2. 参数合法（逐项对照模块 params_schema：枚举值 / 范围 / 类型）
   │  3. 编排合法性：循环次数 ≤ 50（且 ≤ 体力可刷局数）、单步超时 ≤ 模块最大时长、check 跳转目标存在
   │  4. 体力账校验：energy.cost_per_run × 次数 ≤ 当前体力 - 预留，防"刷过头"
   │  5. 资源风险：脚本总时长 ≤ 用户设定上限
   │  6. 隐私风险：截图仅回传至用户自己的 TOS 空间
   │ 通过？──是──► 入库 + 下发客户端执行
   │   └──否──► 附修改意见，回子智能体 1 重写（≤ 3 轮，仍不通过则转人工拒绝）
```

## 11. 通信协议扩展（基于现有消息格式）

沿用现有统一结构（`type / action / data(Base64-JSON) / requestId / timestamp`），新增 action：

| 方向 | type | action | data 说明 |
|------|------|--------|-----------|
| 客户端→服务器 | `command` | `submitTask` | 需求文本 + 截图 TOS 链接 + 设备信息 |
| 服务器→客户端 | `command` | `runDsl` | 编排 DSL JSON（仅引用客户端模块，不含底层原语） |
| 客户端→服务器 | `response` | `runDsl` | 执行结果：完成 / 失败 + 截图列表 |
| 客户端→服务器 | `response` | `executeStep` | 逐步回执（进度上报，含模块返回的 state） |
| 服务器→客户端 | `command` | `stopTask` | 紧急停止当前任务 |
| 客户端→服务器 | `command` | `uploadComplete` | 截图上传 TOS 完成通知（附 objectKey） |
| 客户端→服务器 | `command` | `modsReport` | 客户端模块库清单上报（名称 / 版本 / sha256，供智能体编排与更新判断） |
| 服务器→客户端 | `command` | `modsUpdate` | 模块热更新下发（签名 + sha256 + 压缩包） |

## 12. 非功能需求

| 类别 | 要求 |
|------|------|
| 性能 | 模块内图像匹配单帧 ≤ 500ms；DSL 步骤间调度开销 ≤ 100ms；截图上传不阻塞执行线程 |
| 安全 | 全部传输走 JWT；编排 DSL 执行器白名单硬编码（仅 5 种节点）、模块名 + 参数 schema 校验；模块签名校验（sha256）；TOS 私有桶 + 签名 URL |
| 可靠性 | 断线重连（已有）后续传任务状态；执行中客户端崩溃 → 服务器标记任务失败并通知 |
| 合规 | 客户端启动任务前二次确认"承担游戏账号风险"；提供全局急停快捷键（如 F12） |
| 可观测 | 全链路日志（客户端 / 网关 / FastGPT）；任务报告含每步截图时间线与模块执行结果 |

## 14. 风险与应对

| 风险 | 等级 | 应对 |
|------|------|------|
| 游戏版本更新导致 UI 变化、脚本失效 | 高 | 模板图存 TOS 集中管理；失败截图自动回流 AI 重新识别并更新模板 |
| AI 生成危险 / 失控指令 | 高 | 分层约束：AI 仅可编排白名单模块（参数 schema 校验）+ 子智能体 2 硬规则审查 + 执行器白名单 + 用户急停（多重保险） |
| 自动操作被游戏判定违规 | 中 | 温和操作（不模拟人类点击随机偏移范围）、限速、用户自担风险确认 |
| 图像识别误判（场景相似） | 中 | OCR + 模板双重校验；关键动作前强制截图留证 |
| 网络 / TOS 上传慢 | 低 | 预签名直传 + 压缩 + 失败重试队列 |

## 15. 验收标准（关键场景）

1. 用户在星穹铁道内（任意界面）发起"清开拓力"：子智能体 1 依据截图体力数值计算可刷局数并生成体力编排 DSL，客户端依次调用"刷本""领取奖励"整任务模块执行全流程（选关 → 进本 → 自动战斗 → 结算领取），体力预留与不足分支正确，全程无需人工，成功率 ≥ 90%。
2. 子智能体 1 生成的任意编排 DSL 均被子智能体 2 审查；危险样例（未注册模块名、越界参数、超 50 次循环、超时长）100% 被拦截，且 DSL 无法表达任何底层键盘 / 鼠标原语。
3. 任务执行期间任一节点用户按急停，10ms 内停止所有输入动作。
4. 同一账号重复任务期间，服务器拒绝并发任务下发。
5. 原神任务在星穹铁道验证通过后进入适配，验收标准同场景 1。
